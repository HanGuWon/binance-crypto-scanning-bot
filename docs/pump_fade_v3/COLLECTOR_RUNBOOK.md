Status: **standalone collector implemented and locally tested; not deployed, enabled, or network-started on OCI**. The existing recommender remains untouched. The isolated foreground entrypoint is `python -m signalbot.pump_fade_v3.collector --config config/pump_fade_v3/collector.json --enable --data-mount /var/lib/binance-bot-2/prospective-r` (run from `/opt/pump-fade-v3` with the dedicated virtual environment). `run_standalone` composes the existing capture pipeline, `PublicWebSocketCaptureOwner`, `PublicRestCaptureAdapter`, and `SegmentedCaptureWriter`; it does not import the production scanner, order client, or Discord service. The systemd unit is an inert, non-installable staging template, not evidence of deployment; it has no [Install] section.

OCI read-only evidence (2026-10-08) confirms /dev/sdb mounted at `/var/lib/binance-bot-2/prospective-r` with ~32.4 GiB free; `/data` and `/mnt/data` are absent. Restrict the user to public exchange data: no private keys, Discord token, recommender database, order client or shared application service. The local `config/pump_fade_v3/collector.json` defaults to disabled and must match the mounted DATA path. Service resource caps: `MemoryMax=2G`, `CPUQuota=60%`, `Nice=10`, `IOWeight=50`. No new OCI resources, disk resize or recommender restart is permitted.

This repository includes an executable but opt-in collector. The shipped JSON has `enabled: false`, and the CLI requires both `--config` and explicit `--enable`, which arms the collector in memory without rewriting JSON. The systemd `ExecStart` specifies the same relative config path, `--enable`, and `--data-mount /var/lib/binance-bot-2/prospective-r`; its `WorkingDirectory=/opt/pump-fade-v3` must contain `config/pump_fade_v3/collector.json`, and `ReadWritePaths` is restricted to the matching dedicated collector directory. The runtime rejects a missing, mismatched, or non-mounted DATA filesystem. Installation or starting requires a separately approved staging action. Do not call `systemctl enable`. A failed stage stops **only** the new collector. Do not change the existing `signalbot.service`.

## A3 capacity and two-hour stage

Use the recorded 30-minute baseline in `devlog/_plan/261007_pump_fade_v3/010_l0_oci_gate.md`: recommender normalized CPU p95=17.77%, maximum permissible staged p95=22.77% if close-to-evaluation delay remains unavailable. Record timestamped recommender process CPU p50/p95, voluntary/involuntary context-switch deltas, load/run queue, CPU steal, CPU/memory/IO PSI, and closed-5m close-to-evaluation p50/p99 where timestamps permit. Also record `MemAvailable`, swap-in, OOM, service restarts and classified HTTP 418/429. Stop the staged collector if CPU p95 increases by more than five percentage points when evaluation delay is unavailable; `MemAvailable` falls below 3 GB; memory PSI `some avg10` reaches 5%; load exceeds 1.6; swap-in/OOM grows; a new 418/429 appears; or any measured close-to-evaluation latency degrades beyond the approved baseline. Retain a timestamped failure receipt. Never restart or tune the recommender.

Storage is bounded to **16 GiB across all collector generations**, with a **12 GiB DATA-filesystem free-space floor** and **512 MiB reserved headroom** for emergency coverage. The `DiskBudget` seeds retained-file size at startup, accounts for approved incoming frame bytes across generation changes, and checks filesystem free space before each guarded write. **The first cap/floor breach immediately calls the depth-shed callback, permanently trips the disk guard, rejects the triggering write, and logs CRITICAL; it does not continue non-depth capture after shedding.** The pipeline then fails closed. Its emergency coverage journal may use the writer's reserved bytes without being blocked by the external capacity guard, on a best-effort basis. Never delete unverified or unarchived segments. REST weight budget ≤600/minute, with observed shared-IP Binance used-weight headers checked against 2400/minute; bounded retries honor `Retry-After`, and HTTP 418 opens a fail-closed circuit. Keep at most 25 admitted event symbols with the fixed 26-hour lifetime.

Above **2.0 GB/day**, disable event-scoped `depth5@500ms` entirely and document the change; there is no authorized `depth5@1000ms` fallback. Do not silently prune based on timestamps alone. Retain newest seven days on OCI.

Run the PC script from Windows PowerShell using an existing SSH host alias and matching server-side directory. Example: `powershell -File scripts/oci_capture/pull_verified_segments.ps1 -SshHost <configured-host-alias>`. Defaults are dry-run and no remote prune; `-Execute` opts into copying. For remote deletion use both `-Execute -PruneVerified`, only after inspecting the script, generation receipts, manifests, destination hashes and dry-run receipt. The script selects canonical `capture-<boot>-gNNNN` generation directories, validates segment filenames inside each generation, verifies remote and local SHA-256 digests and copied manifests, and rejects missing or mismatched clean terminal evidence. It never deletes a segment without a matching verified local copy. Configure SSH key/route outside this repository. PC destination: `D:\Binance-trade-analysis\oci-capture`. A segment is eligible only when its manifest's last receipt is older than the newest seven days.

## Unresolved OCI observations

The runtime writes to `/var/lib/binance-bot-2/prospective-r/pump-fade-v3/capture/capture-<boot>-gNNNN/`. Each generation has immutable `generation-receipt.json` and, after clean shutdown, fsync'd `generation-terminal.json` using exact schema `pump_fade_v3_generation_terminal_v1`. Clean terminal fields include `status=CLEAN_CLOSED`, `recovered_crash=false`, `archive_clean=true`, the exact `generation_directory`, `start_sha256` over the **original start-receipt bytes**, `plan_sha256`, `process_boot_id`, `terminal_at_ms`, and `compressed_bytes_by_stream`. The compressed counters sum encoded persisted outer-frame bytes and distinguish actual WebSocket stream names from REST request roles. On startup, unfinished generations are recovered through the same collector disk guard or fail closed; recovered terminal status is `RECOVERED_CRASH_INCOMPLETE`, with `recovered_crash=true`, `archive_clean=false`, the same identity bindings and terminal timestamp, plus an explicit unknown restart-gap marker. Recovery is idempotent; existing terminal identity mismatches fail closed. Only a clean, matching generation qualifies for PC archive/prune consideration. Live, incomplete, or recovered-crash generations are **never** prune-eligible. The producer and offline fixture tests now exist, but remote pruning remains a separate operator-authorized action requiring staged, end-to-end verification.

Optional remote prune requires Python 3 and clean, immutable generation closure. Its single remote operation validates names, non-symlink regular files, a finalized manifest and both SHA-256 digests; renames the pair into a new per-manifest directory under `.prune-staging` on the same filesystem; rereads both digests; then unlinks only the quarantined verified copies. Any rename or post-rename verification failure preserves the quarantine for operator recovery. The two renames are sequential, not one atomic two-file transaction. Until exclusive capture-directory ownership and finalized immutable writer output are verified, leave `-PruneVerified` unused.

Security conditions: disk accounting walks nested entries without following symlinks, reparse points, hardlinks or non-regular filesystem entries; any unsafe entry prevents startup/reconciliation rather than allowing an outside-DATA size read. The PC batch skips missing, live, incomplete or invalid-terminal generations and continues to later generations. Immediately before each remote prune, the PC script re-hashes **local segment, manifest, start receipt and terminal receipt** against the earlier verified digests. The entire destination archive tree must have **exclusive operator ownership and no reparse/junction components**, established outside this script with filesystem permissions; the script does **not** mutate ACLs or establish exclusive locks, and checking only a destination leaf is insufficient proof of safe ancestors. Local hash rechecks and remote rechecks narrow the race but do **not** provide impossible cross-machine atomicity. Keep `-PruneVerified` disabled if exclusive non-reparse ownership cannot be established.
