## Alert contract

`alerts.py` is a pure projection layer over existing L60-04 shadow results and
the existing read-only reconciliation result. It implements exactly the L60-05
required operator alert families:

- `WOULD_UPDATE_STOP`
- `STALE_CONTEXT`
- `MANUAL_SIZE_INCREASE`
- `SIDE_FLIP`
- `PROTECTION_MISSING`
- `RECONCILIATION_UNCERTAIN`

The implementation reuses current Guardian authorities instead of introducing a
second reconciliation state machine:

- `STOP_UPDATE_INTENT` is the source of `WOULD_UPDATE_STOP`;
- `CONTEXT_REJECTED / STALE_CONTEXT` is the source of stale-context alerts;
- `MANUAL_POSITION_ADD` maps to manual-size-increase;
- `SIDE_FLIP_REQUIRES_REAPPROVAL` maps to side-flip;
- `PROTECTIVE_ORDER_MISSING` maps to protection-missing;
- `RECONCILIATION_UNCERTAIN`, `DEGRADED`, or an uncertain context cursor maps to
  reconciliation-uncertain.

Alerts do not dispatch anything and contain `exchange_write_calls=0`.
`WOULD_UPDATE_STOP` explicitly says that no exchange order was sent.

## Fail-closed identity and protection-only checks

Before rendering a stop-update alert the projection verifies:

- intent market is Futures;
- symbol and direction match the durable managed identity;
- `position_ref` exactly equals the canonical full
  `account_alias:symbol:position_side:adoption_generation` identity;
- the intent is reduce-only;
- it is not close-position execution;
- it is effective only from the next candle;
- `order_placed` is false;
- the source result includes a nonblank context ID;
- source result reports zero exchange writes.

Any non-zero exchange-write count or already-placed shadow order fails alert or
report construction closed.

## Deterministic identity and sanitization

- Each alert receives a deterministic SHA-256 `alert_id` over the schema,
  durable identity, stable source reference, event time, and sanitized content.
- The stable source reference affects identity but is not rendered.
- The operations report receives a deterministic SHA-256 `report_id` over its
  canonical sanitized body.
- Identical builder inputs therefore produce byte-equivalent structures and the
  same IDs.

Rendered messages/reports intentionally omit:

- `account_alias`;
- canonical `position_ref`;
- API key and API secret;
- database URL;
- account/wallet balance fields;
- unknown free-form reason strings.

Unknown reconciliation alert strings collapse to
`UNKNOWN_RECONCILIATION_ALERT`. Unknown shadow reason text becomes
`UNSPECIFIED`. Managed position quantity may be rendered because it is position
size, not an account balance.

## Restart/idempotency boundary

Independent adversarial review identified an important boundary: the existing
`ReconciliationResult.alerts` value is an in-process projection, not immutable
historical alert evidence. Replaying an already-applied snapshot can legitimately
produce a different reconciliation notice, and the current account-snapshot
ledger payload does not persist every fact needed to reconstruct every L60-05
alert (for example `protective_order_confirmed`).

L60-05 therefore makes no durable exactly-once alert-delivery claim. The runbook
states explicitly that a freshly recomputed `ReconciliationResult` must not be
treated as immutable restart authority. Durable restart/fault replay and recovery
semantics are the next roadmap task, L60-06.

This boundary is not an L60-05 blocker because L60-05 is the deterministic pure
projection/report contract; delivery/restart replay is explicitly scheduled for
L60-06.

## Operations report

`report.py` builds one sanitized, deterministic `position_guardian_operations_report_v1`
document. It contains:

- managed symbol, side, and adoption generation without account alias;
- sanitized shadow disposition/reason and stop-intent metadata when present;
- sanitized reconciliation state and alert codes when present;
- deterministic required-alert counts;
- operator-attention state;
- report-level `exchange_write_calls=0`.

No network, database mutation, or exchange client exists in the L60-05 owned
implementation files.
