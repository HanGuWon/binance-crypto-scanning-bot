## Context consumer contract

`context_client.py` implements a read-only adapter and a fail-closed local
validation boundary. Before policy evaluation it verifies:

- context version matches supported major `1`; malformed/old/new majors reject,
- the source candle is explicitly closed,
- the `ProtectionContext` schema and deterministic `context_id` validate,
- market, symbol, and primary interval match the managed stream,
- `candle_close_time_ms` is strictly before the consumer clock,
- effective age is `max(now - close, context_freshness_ms)`,
- age equal to `max_age_ms` is allowed and age greater than it rejects,
- the persisted closed-candle cursor cannot regress,
- one close time cannot map to a different context ID,
- malformed persisted cursors reject.

The HTTP adapter uses only `GET /protection-contexts/latest`. API statuses
`NOT_FOUND` and `STALE_CONTEXT` fail closed. No private account data is sent to
the scanner API.

## Pure planner and managed-position identity

`planner.py` composes, rather than duplicates, the existing L60-01
`ProtectiveStopPlanner` and `StopUpdateIntent` contract.

- managed snapshot and public context must be USD-M Futures and symbol-equal,
- `snapshot.observed_at_ms` must equal the same closed-candle cursor,
- LONG uses confirmed swing support and SHORT uses confirmed swing resistance,
- `consecutive_trend_failure_count > 0` supplies the existing explicit
  weakening input,
- stale/uncertain managed context remains no-intent through the existing pure
  planner,
- the existing planner keeps monotonic/reduce-only/next-candle semantics.

Runtime validates the durable adopted identity before context or policy work.
The canonical `position_ref` is:

`account_alias:symbol:position_side:adoption_generation`

Wrong account/generation refs reject before context validation or policy
evaluation.

## Deterministic identity and persistence

- Same managed snapshot + same validated context + same policy inputs produce
  the same existing `StopUpdateIntent.intent_id`.
- Planned-intent ledger event IDs additionally hash the full managed identity
  (`account_alias`, symbol, side, adoption generation) plus `intent_id`, so two
  account/generation identities cannot alias the same ledger event ID.
- The closed-context reconciliation cursor event ID is deterministic from the
  context stream name and `context_id`.
- `GuardianRepository` append-only same-event semantics make rerun/restart a
  no-op rather than a duplicate row.
- A crash after intent persistence but before cursor persistence converges on
  replay: the intent event is idempotent and the cursor can be appended safely.
- A persisted non-`CERTAIN`/`DEGRADED` context cursor blocks shadow planning and
  creates no stop intent.
- A valid context that yields no policy update may advance the consumed context
  cursor without creating an amend intent.
